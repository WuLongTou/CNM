# CNM 贴图管线：萌系卡通、生成即定稿、游戏侧直接 clip

## 一、核心理念（业内 2D 条带常规做法）

- **生成即定稿**：提示词完整、准确、无歧义，直接规定行列布局、每帧像素格与风格；不合格的图直接用 Gemini 重生成，**禁止用后处理修补**（不浪费时间去修）。
- **后处理只做无损分割**：沿空白间隔裁切，禁止缩放、拉伸、改色、去纹理。
- **游戏侧直接 clip**：整张长图进内存，按 atlas 真实矩形偏移取帧，不做运行时缩放。
- 统一管理靠合同 + 测量核验：超差/帧数不符即重生，不准拉伸修复。

## 二、风格合同（萌系卡通，全项目贴图统一）

- **基调**：可爱卡通、Q版萌系二头身——头大身圆、四肢短圆、圆滚滚软乎乎、表情呆萌憨态。
- **眼睛**：全项目统一萌眼——玩家纯黑墨点大圆眼 + 小白高光；妖物大而圆的炭黑色萌眼 + 两个大小白高光圆点（毛绒玩具感），目光呆呆的。**任何角色绝不红眼/发光眼/斜吊眼**（血红只作符纹、徽记等配色点缀，不上眼睛）。
- **上色**：色块填充干净柔和明亮，炭棕色(#332e29)圆头均匀粗描边；无渐变、无阴影晕染、无纹理颗粒；纯白背景（地面类除外）。
- **妖王 = 大块头小表情**：体型放大的呆萌大头目，气场靠体型、骨冠/符纹等道具表达，表情依然呆萌；提示词禁用「威严、怒容、怒视、气势逼人、威压」等凶恶词。
- **一致性铁律（提示词必须逐字带上）**：同一张图内所有帧/格子必须是同一个角色/同一套物品——脸型、头饰、体型、配色、描边粗细、占格大小逐帧完全一致，「像同一个角色剪出来的贴纸排」；严禁风格漂移、严禁画成不同角色、严禁个别帧画风突变。
- 所有角色帧严格面朝右、同一基线、大小一致。

## 三、合并出图（同类小图拼一张）

- 同尺寸小图必须合并出图：动画帧一条带、武器/道具图标一张网格（每行不超过 3~4 格防缩水）。
- 大格网格图可在格间留清晰空白，方便沿空白分割；**严禁模型画格线/边框**。
- 整幅大图（地面、全屏背景）单独出，不并入网格（分辨率不可牺牲）。
- **长尾/飘带类角色**：尾巴、飘带、武器尖严禁伸入相邻帧的空白区（会桥接间隙导致分割粘连）；提示词逐帧要求“不越界”。
- **动作动词决定越界（enemy_dragon 连续 6 轮粘连带血的教训）**：泛泛的「不越界」「绝不越进相邻帧」模型基本不听——「原地扑击、前爪向前扑出」这类横向动作词必然诱发身体横拉越界（帧间出现 300~500px 的粘连大段）。已验证一次通过的写法：把动作改成纵向（如「原地垂直向上小跳」），并显式加三条硬约束：「身体始终保持团状紧凑轮廓」「每一帧外接框大小完全相同」「严禁伸长脖子/身体/尾巴，尾巴短小贴身」。同一图连续失败 ≥2 轮时，先审视动作动词本身，不要反复重掷骰子。

## 四、网格合同（提示词必须逐字落实）

- 动作条带一律单行：敌人 attack / walk 各 6 帧、玩家按动作单张（walk 8、attack 6、dash 4、hurt 2、death 6）。
- **帧数弹性（实测模型约束）**：提示词按上述帧数写，但行走/冲刺/死亡类循环模型常出 7~10 帧——只要条带内部等分一致、无粘连，按实际帧数切帧入库（atlas 真实矩形，游戏按帧数循环播放，任意帧数可用）；**受时间轴约束的除外**：attack 6 帧（出手时长映射）、hurt 2 帧（受击反馈）不符即重生。
- 每帧为等大方格：角色类 128x128，整行宽高比 N:1；妖王单张 256x256；武器道具网格每格 256x256。
- 角色占格约七成并居中，双脚或身体底边落同一基线；动作不得画出格子；帧间距清晰、互不重叠。
- 图标格内每物品只出现一次，严禁重复格；无文字、无边框、无序号、无阴影、无地面线。
- **禁圆圈包围**：不要给角色画圆圈、椭圆、气泡框等任何包围线条（模型爱用“动作圈”装饰，游戏里会穿帮）。

## 五、全链路尺寸契约（生成前先定，2026-09-25 玩家条带半身事故沉淀）

**生成端出的图必须按下游消费方式反推规格**，规格只定「帧数」不定「画布像素布局」就会全链路错位（实测事故：warrior_walk sidecar 10 帧×100.9px 旧测量套 8 帧新图 → 游戏内半身/消失交替）。

- **画布规格（提示词逐字带上）**：输出图宽 = 帧数 × 帧格宽（角色类 128，妖王 256），即 8 帧 = 1024px 宽；高 = 帧格高。首帧内容从第一格内开始，不允许整条内容缩在画布一侧。
- **帧内容规格**：每帧内容以格为界居中、占格宽 ≤70%、底部同一基线、任何笔画不出格；帧与帧之间靠「格边界」隔离，不靠随机空白。
- **验收量化（verify-stage 必测，超差即拒收重生）**：① 段数 = 帧数；② **段步长一致性**：相邻段起点差极差 ≤4px（实测 warrior_walk ±1 合格、attack 类 ±25 会造成游戏内帧内容跳动）；③ 内容 span ≤ 画布宽且 ≥ 帧数×格宽×50%。
- **布局归一化 ≠ 内容修补**：帧数与画风合格、仅步长不均的条带，允许做「无损重排」——按实测段边界把每帧内容原样搬移到标准网格位置（只改水平位置/补画布，不缩放不改色），重排后整链路回到简单等分；这是解决「模型画不匀步长」的兜底，优先级低于重生（重排前先重掷一次）。
- **下游消费契约**：sidecar 记录实测 {frames,h,step,span,segs}；sync 的 clipSheet 按 sidecar 等分窗口（步长均匀时无损）；view 层按 meta.cnm.bandH 整条等比缩放、帧索引按 frames.length 动态取模（任意帧数兼容）。

## 六、后处理铁律（post 与 sync-assets）

- 只允许：边缘泛洪去白底、沿空白间隔裁切、原样落盘。
- 禁止：resize、fit、拉伸、改色、锐化。凡经缩放的产物一律视为中间态，入库前用 split-only 流程从 raw 重切。
- 每张产物必须附测量报告：行列数、内容总跨度、等分步长、每格实测宽。帧数不符或跨格粘连即判失败回去重生；步长取整误差不超过 1px。
- atlas 记录真实裁切矩形，游戏按矩形 clip，不依赖固定步长假设。

## 七、质检门（每张必过，不合格直接重生）

- 行列数与帧数吻合提示词（玩家 walk=8、hurt=2；敌人每行 6 帧）。
- **网格合规按第五节量化验收**：段步长极差 ≤4px、span 在 [50%,100%] 画布宽区间；超差先重掷、再无损重排。
- **跨条带角色锚点必须逐字一致**（2026-09-25 ranger 事故：walk 写"绝不变成马尾"、idle/death 写"深棕色高马尾"，模型忠实执行画成两个人——先对齐 prompts 文本再怪模型漂移）。
- **入库前必须过视觉门**：拼六动作首帧对比图（qc/*-consistency.png）目检是否为同一人；帧数核验通过≠角色一致，不目检不 deploy。
- 萌系风格达标：圆滚滚呆萌，无凶相；同图多帧风格一致。
- 无边框、无文字、无序号、无重复格；背景纯白可去净；基线一致；间隔干净无粘连。

## 八、当前管线位置

链路顺序：prompts 提示词（含画布规格）→ raw 生成图 → post.mjs 切帧+测量 → stage 产物 → verify-stage.mjs 量化验收 → deploy-assets.mjs 入库 assets-src（png+sidecar）→ sync-assets.mjs 生成运行时 atlas（public/assets）→ view.ts 按 bandH 等比渲染。任一环的规格改动必须同步上下游。

- 驱动：.workwork/gemini-gen/as_gen3.mjs（daemon + 队列，2026-09-25 重构实测）：
  - **专用独立 Chrome 实例**：独立 profile（chrome-profile/）+ 独立端口 9223，与用户日常 Chrome 完全隔离；**绝不连 9222**——那是日常 Chrome 的调试端口（lsof 可证），每次 CDP 重连都会向用户弹「请求远程控制」。
  - **常驻 daemon + 队列**：`node as_gen3.mjs --daemon` 长驻、只建一次 CDP 连接；生成任务 `node as_gen3.mjs <pid>...` 经 gen-queue/ 投递；WS 断线退避自愈（重连 ≤3 次后退出），严禁 kill/重连循环。**提交级会话隔离**：默认每次提交开启全新对话（session.reset 哨兵），`--continue` 才延续旧对话——`chatWho` 常驻内存跨提交复用是祸根，长对话后段必劣化（动作内容互换、帧数乱来，2026-09-25 实测 death/idle 内容对调）。复杂动作优先单独提交；先投 idle 单张验证角色，确认后再 `--continue` 投剩余。**空闲 WS 会被掐断**（2026-09-25 实测：dragon 生成完数分钟后静默断开且无任何操作）：connect 成功后必须起 30s 间隔的轻量 CDP 保活（如 Browser.getVersion），断线日志要记 close code/reason。**重连必须先清空旧 sessionId**（2026-09-25 实测：不断其 WS 断后重连三连败 `Session with given id not found`，因新连接首个请求带了 stale 会话）。
  - **Chrome 111+ 握手细节**：browser WS 只认 `/json/version` 返回的带 UUID `webSocketDebuggerUrl`（`/devtools/browser` 短路径 404）；请求带 Origin 头会 403，客户端不得发送。
  - **AI 会话沙盒内起不来 Chrome**（内层沙盒嵌套冲突，详见全局 sandbox-adaptation skill）：实例必须在沙盒外拉起——用户终端执行 `bash .workwork/gemini-gen/chrome-start.sh`（后台窗口不抢焦点，内含清残留锁与端口等待）；daemon 侧 ensureChrome 只做端口探测与清晰指引，不做启动重试。
  - 后台事件分发：真实坐标 Pointer/Mouse 事件序列配合 input/change 派发；严禁窗口激活/置顶、严禁强切标签页。
  - 全量核验：`node verify-stage.mjs`（段数=帧数，不足判粘连 FAIL；walk/dash/death/idle 弹性帧数 7~10 为 WARN 允许）。
- **extract 按视觉最低位置选图**（最新回复在最下方；DOM 末尾在长对话里不可靠——历史图重渲染产生新 blob URL，2026-09-25 实测 hurt 存成 death 复件）；**字节去重守卫**：新图与已有 raw 复件字节相同直接报错走重试，不静默入库。daemon 改代码后必须重启生效（常驻进程不热更新）。
